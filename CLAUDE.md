# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Two things layered in one repo:

1. **A workshop**: "Working with Claude, London" — a hands-on Claude Code course. `workshop/` holds the lab instructions (`lab-3-ship-todo-231`, `lab-4-fit-it-to-you`, `lab-5-put-more-agents-on-it`), `docs/tickets/` holds the sample backlog (TODO-231/232/233) the labs work through, and `docs/examples/` holds reference material (a CI workflow template, subagent definitions, a skill template, a hook example) that the labs copy into place.
2. **The sample app**: `ops-dashboard`, a small ops dashboard for a fictional coffee-equipment company, Marlowe & Finch. This is the actual codebase most edits touch.

The app: a Spring Boot REST API over PostgreSQL, plus a plain-JavaScript page (no framework, no build step) served as static resources from the same app. It shows four KPI tiles, two inline-SVG charts, a late-deliveries table, and vendor contracts coming up for renewal — reading `orders`, `deliveries`, `tickets`, `carriers`, and `vendors`, all with plain SQL (Spring JDBC + Flyway, no JPA).

The data is synthetic, generated by `tools/make_seed.py` (~1,900 orders/deliveries over the 90 days before 2026-09-21, 600 tickets, 8 vendor contracts). One carrier, Kessler Logistics, is deliberately made to look bad — that's the story the dashboard exists to tell.

**The app's clock is pinned to 2026-09-21** (`ops.today` property, `ClockConfig.java` bean), so KPIs, "days until renewal," and every test assertion agree regardless of the real date. Default date range everywhere is "the last 30 days ending today."

## Commands

```bash
# Run with PostgreSQL (the default)
docker compose up -d db      # Postgres 16 on localhost:5432, db/user/password all "ops"
./mvnw spring-boot:run       # http://localhost:8080; Flyway applies migrations + seed on first start

# Run without a database (no Docker needed — also what tests use)
SPRING_PROFILES_ACTIVE=demo ./mvnw spring-boot:run   # in-memory H2 in Postgres mode, same migrations/seed

# Test
./mvnw test                  # Java: 25 tests (JUnit 5, H2, MockMvc) — always runs on the demo profile
npm install                  # once
npm test                     # Frontend: 45 tests (Jest + jsdom)

# Single test
./mvnw test -Dtest=DashboardRepositoryTest              # one Java test class
./mvnw test -Dtest=DashboardRepositoryTest#kpisForTheLast30DaysMatchTheAnswerKey  # one method
npx jest src/test/javascript/api.test.js                # one Jest file
npx jest -t "renders the KPI tiles"                     # by test name
```

Reset the local database: `docker compose down -v` (drops the volume; Flyway reseeds on next start). Override connection details with `DATABASE_URL`, `DATABASE_USER`, `DATABASE_PASSWORD`.

## Architecture

**Not a client/server split** — there's one deployable. Spring Boot serves the JSON API under `/api` *and* the static frontend (`src/main/resources/static/index.html`, `app.js`, `style.css`) from the same origin. The frontend's `app.js` calls `/api/...` with relative `fetch()` paths; no CORS, no auth, no proxy config, no base-URL env var to know about.

Backend layering, all in `src/main/java/com/marlowefinch/ops/` (flat package, no sub-packages):
- `OpsApplication.java` — entry point.
- `ClockConfig.java` — the pinned `Clock` bean; every "today"-relative calculation in the app depends on it, not `LocalDate.now()`.
- `DateRange.java` — resolves `from`/`to` query params, defaulting to the last 30 days. Deliberately has no input validation (a malformed date throws and surfaces as a 500, `from` after `to` just returns empty) — that gap is tracked as TODO-232, not a bug to silently fix.
- `DashboardRepository.java` / `VendorRepository.java` — all the actual SQL and business rules (e.g., what counts as "on time," how renewal notice windows are computed) live here via `NamedParameterJdbcTemplate`, not in an ORM layer.
- One thin controller per resource: `KpiController`, `DeliveryController`, `TicketController`, `VendorController`, `HealthController` — each just parses params, calls the repository, and returns a response record (`Kpis`, `CarrierOnTime`, `LateDelivery`, `TicketCategoryCount`, `Vendor`).

Data model: `db/migration/V1__schema.sql` (schema) and `V2__seed.sql` (seed data, generated by `tools/make_seed.py`) — Flyway runs both on startup in every profile.

Two Spring profiles matter: `postgres` (default, real Postgres via docker-compose) and `demo` (in-memory H2 in Postgres-compatibility mode — what the test suite and no-Docker/Codespaces/web usage run on). Both apply the same migrations and seed, so results are meant to be identical between them.

## Testing conventions

- Java tests assert against a fixed "answer key" (see `docs/data/ANSWER-KEY.md` and `DashboardRepositoryTest`) derived from the seed data — e.g., exact on-time rate, exact revenue for the default 30-day window. If you change the seed generator or the schema, these expected numbers must be regenerated, not hand-adjusted.
- `MigrationsTest.java` checks Flyway applied both migrations and that row counts match the generated seed (1934 orders, 1859 deliveries, 600 tickets, 8 vendors).
- Frontend tests boot the real `app.js` inside jsdom via a harness (`src/test/javascript/setup/loadApp.js`) that stubs `fetch` with canned fixtures — they exercise actual client code, not mocks of it.
- `harness.test.js` cross-checks that every DOM id in `index.html` is registered in the harness's `REGISTERED_IDS` list. Adding or renaming an element in `index.html` requires updating that list or the test suite fails.

## Constraints to respect

- `pom.xml` dependencies are frozen — the file header says changes require a CHG ticket. Don't add/upgrade Maven dependencies without flagging that explicitly.
- `.mcp.json` registers a read-only `postgres` MCP server (every query runs in a `READ ONLY` transaction) pointed at the local compose database — treat it as query-only, not a way to modify data.
- There is no `.github/workflows/ci.yml` yet by design; `docs/examples/ci.workflow.yml` is the template meant to be copied in (part of the workshop labs), not a sign CI is already wired up.
